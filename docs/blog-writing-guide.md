# Blog Writing Guide — Deep Analysis Series

This blog is **not** a tutorial blog. It is a technical-analysis blog for senior practitioners. The goal of every post: teach something the reader **cannot easily find anywhere else** — by going deeper than the docs, covering the edge cases the docs omit, and showing the trade-offs only experience reveals.

If a post reads like it could have been generated by copy-pasting docs or a quick search result, it fails. Rewrite it.

## Core principles

### 1. First-principles depth
- Explain *why* something works the way it does (protocols, RFCs, internals), not just *how* to use it.
- Trace the full path end-to-end (e.g., request → TLS handshake → chain validation → server), not a single step.
- Never stop at "this works." Ask: **what actually happens at each layer?**

### 2. Edge cases are the content
- Every post must have a dedicated section on edge cases: what breaks, weird inputs, limits, boundary conditions.
- Real examples: empty input, huge payloads, concurrency, locale/timezones, partial failures, retries, expired state.
- Ask: **what does a 0.1% occurrence look like, and how do you handle it correctly?**

### 3. Pitfalls / mistakes ("the traps")
- Cover the common and subtle mistakes people make — especially ones that *look* right but fail in production.
- Include the failure symptom so readers can recognize it (error messages, stack traces, weird behavior).
- Explain the underlying cause and the correct approach.

### 4. Best practices & production hardening
- End each topic with what "doing it properly" means: security defaults, observability, failure handling, perf, code organization.
- Explicitly flag what to do for **local/dev vs production** — they differ.
- Where there are legitimately multiple good approaches, compare trade-offs (cost, complexity, failure modes) and give a recommendation with reasoning.

### 5. Rare / non-obvious knowledge
- Prefer subjects and angles rarely covered: internals, debugging stories, performance gotchas, protocol subtleties, security foot-guns.
- Include *your* experience: what surprised you, what you debugged at 2am, what burned you. First-person experience is the differentiator.

## Structure of a post

```
1. Hook / TL;DR        — the core insight in 2–3 sentences, honest about scope
2. Foundation          — first-principles groundwork (keep tight, link docs, don't re-teach basics)
3. Core walkthrough    — the main mechanism, traced end-to-end with code
4. Edge cases          — dedicated, detailed, with correct handling
5. Pitfalls            — the traps, with symptoms + causes + fixes
6. Best practices      — production checklist, trade-offs, recommendations
7. "The part they don't tell you" — the rare insight / your war story
8. Summary / checklist — actionable recap
```

## Voice & tone

- **Experienced engineer, not a marketer.** No hype, no "in today's fast-paced world." Direct, precise, confident.
- Write like you're explaining to a sharp colleague over a whiteboard — assume intelligence, not knowledge.
- **Precise terminology.** Use the correct protocol/API names. Never hand-wave ("it just works", "magically").
- **Honest about trade-offs.** State what's a bad idea and why, what's situational, what you'd pick and why.
- First person is fine and encouraged for experience ("when I hit this in production…"). Never fabricate.

## Formatting rules

- Use code blocks with correct language and realistic, runnable-looking code.
- Show failure output (errors, stack traces) so readers can recognize it.
- Use tables for comparisons (approach / cost / failure mode / when to use).
- Keep paragraphs tight; deep ≠ verbose. Density of signal matters more than length.
- Prefer specific numbers over vague claims (e.g., "~200 ms for a 2 KB body over TLS 1.3").
- Every claim about defaults/behavior should be verifiable or flagged as "in this version."

## Content checklist before publishing

- [ ] Covers at least one **edge case** most articles miss
- [ ] Has a **pitfalls** section with symptoms + cause + fix
- [ ] States **best practices** with explicit trade-offs
- [ ] Contains at least one **rare/non-obvious** insight
- [ ] First-principles explanation of the *why*
- [ ] No filler, no marketing tone, no doc-copy-paste
- [ ] Frontmatter matches schema (see AGENTS.md), `draft: false` to publish

## What this blog is NOT

- ❌ Tutorials that just re-run official examples
- ❌ "Top 10 listicle" content
- ❌ Re-statements of documentation
- ❌ Content written for beginners who don't know the basics
