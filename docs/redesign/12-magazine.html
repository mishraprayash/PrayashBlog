The outbox,and five waysit breaks

Skipped events, bloat, stalled partition drops, and a CDC slot that fills the disk. Every failure reproduced on Postgres 16.

Published9 Sep 2026Revised18 Oct 2026Reading13 minTested onPostgres 16.15

This code has a bug that won't show up in review or in staging. If the Kafka call fails after the insert has committed, the order exists and nothing downstream hears about it. Billing never charges, inventory never reserves, and there's no error anywhere, because from the point of view of the code that made it, the database write succeeded.

● dual-write.tsbroken
await db.orders.create({ data: order });
// ← process dies or broker times out hereawait kafka.send({ topic: "orders", messages: [{ value: JSON.stringify(order) }] });

The usual answer is the transactional outbox: write the event into a table in the same transaction, and let a relay publish it. Scroll through what that buys you, and where it breaks.

Step 01 · the dual write

Two systems, no shared commit

The order commits to Postgres. The publish to Kafka is a separate call, and when it fails, the event is simply gone.

Step 02 · the outbox

One transaction, then a relay

The order and its event are written together, so both commit or neither does. A relay reads the outbox table and publishes.

Step 03 · the ghost row

The relay skips row 1

Ids are handed out on insert, not commit. Row 2 commits first, the relay moves its cursor past it, and row 1, committed later, is never published.

Step 04 · the full disk

A stalled slot fills pg_wal

With CDC, a stopped connector makes Postgres keep every WAL file. On a full disk: PANIC: No space left on device.

01 · data lossThe poller that skips rows

The obvious relay remembers the highest id it has published and asks for anything newer. It loses events whenever two transactions commit in a different order from the one they got their ids in. Run it yourself, then switch the query.

    A replication slot is a promise: Postgres keeps every WAL file the slot hasn't confirmed, however long that takes. Since Postgres 13, max_slot_wal_keep_size caps it, and past the cap Postgres gives up on the slot instead of on the database.
